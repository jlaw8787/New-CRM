## 2. WORKFLOW-AUDIT.md claims, re-verified
====================================================================

**a. Accepting a submission does not create a contract or cascade anything.**
NO LONGER TRUE. Checked `setSubStatus()` (index.html:3304 to 3339): when a submission's status becomes 'Accepted', it sets `c.phase='Offer'` (3323 to 3327) and, if no contract exists yet for that submission, calls `openContractModal(subId)` (3328 to 3329), which opens a pre-filled contract creation form. `saveContract()` (8883 to 8924) inserts into the `contracts` table and, on success, advances the candidate to `phase='Contract'` (8913 to 8916). This is a real, working cascade from Accepted through to a created contract and two further phase advances — the audit's original claim no longer holds.

**b. Candidate phase is only set in one place (sfConfirm) and cannot move past "Submission".**
PARTLY TRUE. Phase can now move further than the audit found: three assignment sites exist (`sfConfirm()` sets 'Submission' at 11068 to 11069; `setSubStatus()` sets 'Offer' at 3325 to 3326; `saveContract()` sets 'Contract' at 8914 to 8915), so phase does advance past Submission to Offer and Contract automatically. But it still stops there — grepped every `.phase=`/`phase:` assignment in the file (candidate seed data aside) and found no site that ever sets phase to 'Travel & Onboarding', 'On Assignment', 'Redeployment', or 'Extension/Exit'. And the audit's other claim — no manual override exists anywhere — is still fully true today: grepped for `EC.phase`, any phase-related `<select>`, and "override" near "phase", zero matches. So: partly true. The single-transition claim is outdated (there are now three transitions, not one), but the "stuck partway through the pipeline with no way to move further, manually or automatically" problem is still real, just further along than the audit described.

**c. Submissions have no start_date or end_date and never capture one.**
NO LONGER TRUE. `submissions.start_date`/`end_date` are captured in the submit flow (`#sf-start-date`/`#sf-end-date` inputs, 10481 to 10482), saved on confirm (11031), and read back by `mapSubmissionRow()` into `startDate`/`endDate` (11109). This matches KNOWN-ISSUES.md item #3, which documents this as built but notes the dates aren't yet displayed on the Submissions list/pipeline board (a separate, still-open display gap, not a capture gap).

**d. Travel, accommodation, car hire and expenses have no create path.**
NO LONGER TRUE. Confirmed insert calls for all four inside the Manage Placement flow: `flights` (6867, 9231), `accommodation` (9382), `car_hire` (9527), `expenses` (9661), plus `openManagePlacement()` (10196) as the entry point. This matches KNOWN-ISSUES.md item #11, logged there as Fixed via PLACEMENT-SETUP-BRIEF.md.

**e. An expired compliance item shows a green Verified badge on the Compliance tab while Alerts flags it as expired.**
STILL TRUE. Checked `renderCpCompliance()` (index.html:5132 to 5187): the displayed status badge reads directly from the stored field, `var st=it.status||'Not Started'` (5165), with no comparison against the item's expiry date at render time — an item whose expiry has passed but whose stored status is still 'Verified' will render the green 'Verified' badge (`b-ok` class) exactly as the audit described. `getAutos()` (1783) is unchanged in this respect — it still computes expiry dynamically for alerts, so the two screens still disagree. This matches KNOWN-ISSUES.md item #1, which is still logged as Open.
